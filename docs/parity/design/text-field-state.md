## Where it starts

The value-based `BasicTextField` is a node, `TextFieldNode`, holding a working copy of its text, cursor, anchor and composition, which every input path edits: keys, the pointer, semantics actions, the desktop's preedit, and the keyboard's edit commands in bytes (`KeyInputModifierNode::on_edit_commands`, D1664). The host's input session reads the node, not the application: `input_method_value`, `input_method_value_is`, `take_input_method_restart`, `cursor_anchor`. That is what the state-based field needs: the session talks to a node, and the node, not the session, decides where its value lives. So the state-based field is the same node with another source of truth. The value-based field stays exactly as it is.

## The state model

**`TextFieldState`** is a state holder, a `Copy` handle as D240 has them (`TextFieldState::new(text)` and `TextFieldState::with_selection(text, selection)` return its `Owned` owner, `remember_text_field_state` keeps it in the composition, saved). It holds one snapshot state, Compose's `value`: an immutable `TextFieldCharSequence` of the text (an `Rc<str>`, so a read copies a pointer), the selection and the composition, compared by content so an edit leaving them as they were invalidates nothing, as Compose's `mutableStateOf` with structural equality. `text()`, `selection()` and `composition()` read it, observed. Offsets are bytes (D1100), `usize`: Compose's negative indices have no counterpart.

**`edit`** is Compose's: a `TextFieldBuffer` over the current value, the block run on it, then committed: a text change commits the composition (what the keyboard composed is the keyboard's to redo), as does a selection change; nothing changed writes nothing. Nested editing panics with Compose's message, read from an `is_editing` snapshot state without observing it; a panic inside the block leaves the state as it was and editable. The block can't suspend in Rust, so Compose's concurrent-coroutine case is the nested one.

**`TextFieldBuffer`** is a `String` with a selection, a composition and a change list, Compose's operations Rust-shaped: `replace`, `append` (a `&str`; the range form is a slice), `append_char`, `insert`, `delete`, `char_at`, `as_str` (`asCharSequence`), `length`, `selection` and `set_selection` (panicking outside the text), `has_selection`, `original_text`, `original_selection`, the cursor placements, `select_all`, `revert_all_changes`, `changes`. An edit moves the selection as Compose's `adjustTextRange`. `std::fmt::Write` is its `Appendable`. A gap buffer has no counterpart: a field's text is short, and `String::replace_range` is what the value field does.

**`ChangeList`** is Compose's `ChangeTracker` ported (changes merged when they touch or overlap, in text order, each with its range now and in the original), with Compose's names: `change_count`, `get_range`, `get_original_range`, `for_each_change`, `for_each_change_reversed`. A transformation iterating while it edits is the buffer's `for_each_change(|buffer, range, original| …)`, re-reading the count as Compose's loop does, since a closure borrowing the list can't edit the buffer.

**User edits** go through `edit_as_user`, Compose's `editAsUser` without a transformation yet. In step 1 the node's edit lands as one replacement found by the common prefix and suffix (`setTextIfChanged`); from step 2 the node reports each edit's real range into the buffer (the commands' ranges, a key's deletion, a paste), with its hardware-source flag, since undo merges by where a change is (typing "a" at 1 of "aa" is an insertion at 1, not the diff's 2) and step 3's transformations read the changes. The selection and composition as the node left them, and the input method is told by Compose's rule: restart only when the content changed under a composition, never for the keyboard's own edits (`restartImeIfContentChanges = false`). The listeners of that rule are Compose's `NotifyImeListener`, kept internal: a node registers one from its creation to its release, and it sets the node's restart flag.

**Composition** is in the state, as Compose's (D1663 already made it part of the value-based field's value): a programmatic `edit` that changes the text or selection commits it, and a node seeing that its composition went (an edit from elsewhere) ends a desktop preedit as `end_composition` does (D1668).

**Undo** is Compose's `UndoState` in the state (step 2, D1132): `TextUndoManager`'s staged operation and `UndoManager`'s two state lists, user edits merging by Compose's rules, programmatic ones never, undo and redo applied without side effects; the state-based node's Cmd+Z and Ctrl+Y go to it, and the node keeps no history of its own. The node's `EditProcessor` keeps what its commands replace (`track_edits`), so the state's changes are where the edits were.

## The field over the state

`BasicTextFieldOfState(state, modifier, enabled, read_only, text_style, keyboard_options, line_limits, interaction_source, cursor_brush, decorator)` (Compose's order; the parameters of later steps, `input_transformation`, `on_keyboard_action`, `on_text_layout`, `output_transformation`, `scroll_state`, come in their places). The name follows `NavDisplayOfState` (D704's row on Navigation 3): Rust has no overloads, and the value-based `BasicTextField` keeps its name.

Its element makes the same `TextFieldNode`, with a link to the state in place of `on_value_change`. The node:

- **adopts** the state's value when it differs from what the node last saw or wrote: when created, when measured (the read is the layout's, observed, so a programmatic edit measures it again, and a measurement asks its semantics anew), and at the start of every event it handles, for an edit made since the last frame. (Built so; an `ObserverModifierNode` was the first plan, but an update giving another state has no context to observe it with.) A new text clears the node's history and paragraph; a composition the state no longer has ends the node's.
- **publishes** what it changed at the end of every event it handles: the text, selection and composition, through `edit_as_user`, the keyboard's own commands marked as such. Selection-only moves (arrows, clicks, focus loss collapsing the selection) write the selection, as Compose's field does.
- never waits for an application: the value-based field's `awaiting_value` undo of an edit not taken (D96) is the value path's only.

The input session reads the state (`input_method_value` and its comparison), so an edit of the state made since the node's last event is what the keyboard's next commands are read against; the node's copy equals it after every event. A frame's restart is the node's own (focus, D1671) or the listener's. A key's edit restarts nothing when an on-screen keyboard sent it (`KeyEvent::from_soft_keyboard`, Android's `FLAG_SOFT_KEYBOARD`), as Compose's key handler.

## The rest, and how each maps

- **`TextFieldLineLimits`** is an enum: `SingleLine`, `MultiLine { min_height_in_lines, max_height_in_lines }`, `DEFAULT` the unbounded multi-line, `TextFieldLineLimits::multi_line(min, max)` validating as Compose's constructor (the field validates a hand-built one too). It maps onto the node's `single_line`, `min_lines`, `max_lines`. Compose's single line also shows a new line as a space and a carriage return as nothing (`SingleLineOutputTransformation`); that is an output transformation, step 4 (D1134).
- **`InputTransformation`** (step 3, D1133): an application's is the trait `InputTransform` (`transform_input(&self, buffer)`, `keyboard_options`, `apply_semantics`); the field takes the value `InputTransformation` (`new`, `from_fn`, `then`, and Compose's `by_value`, `all_caps`, `max_length_trim`, `max_length_reject` as its constructors). It runs inside `edit_as_user` on a buffer whose original is the value before the edit and whose changes are the edit's, as Compose's `commitEditAsUser`; a transformation changing the edit commits the composition, and the node adopts the result. Its keyboard options fill the field's unspecified ones (`keyboard-options-parity`'s `fill_unspecified_values_with`).
- **`OutputTransformation`** (step 4): `transform_output(&self, buffer)` on a buffer of the state's value, its changes giving an offset mapping both ways (`OffsetMappingCalculator`), the cursor kept out of replacements. The node already shows a transformed text through `VisualTransformation`'s mapping (D147); the output transformation becomes a source of that mapping, so drawing, hit testing and semantics need no second path. But `OffsetMapping` lacks `TransformedTextFieldState`'s rules: a cursor kept out of a replacement with a wedge affinity (which side of an insertion it sits on), a selection widened over a replacement, and the input method reading the untransformed text. So the shared node needs a second kind of mapping for the state path, with those rules, beside D147's for the value path. Built so (D1134): `ShownMapping::Output` beside `ShownMapping::Visual`, the keys' motions and deletions made in the shown text; the input method reads the shown text, its commands' offsets mapped back (D1135).
- **`KeyboardActionHandler`** (step 3, D1133): `on_keyboard_action(perform_default_action)`, the default being what the node's `perform_ime_action` does (`Next`, `Previous` move the focus, `Done` hides the keyboard). It runs after the event, as every application callback a field calls, its default action through the `FocusManager` and `SoftwareKeyboardController` read where the field is composed.
- **The decorator** is the value field's `decoration_box`, named `decorator` (`impl Fn(Callback)`, as Compose's `TextFieldDecorator.Decoration(innerTextField)`): the same box, semantics and taps (D102).
- **`BasicSecureTextField`** (step 6, D1142) sits on the output transformation (a mask per glyph, Compose's output-only path; the codepoint transformation, its older path, isn't ported) and an input transformation (the last typed character revealed).
- **Styles in the state** (`text-field-styles`) wait for the rest: the buffer gains a style buffer then.

## Costs

The value-based field gains one field (the link, `None`) and a branch at each event's start and end. `field_keystroke`, `field_keystroke_direct` and `field_focus` are measured before and after each step by retired instructions.

## Risks

1. **Two copies of one value.** The node's copy and the state can disagree between an edit made elsewhere and the node's next event or observation. Every entry point adopts first, and every exit publishes, so the window is inside one event; a test edits the state between two keys of one frame.
2. **Two fields over one state.** Each node adopts what the other published, through the observation; the one with the focus owns the input session.
3. **Writes during layout.** A tap resolved at measurement (`pending_tap`) moves the selection there, so the node writes the state while measuring: allowed (the tree drains writes after layout), at the cost of one more pass that frame.
