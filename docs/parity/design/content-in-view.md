# The animated `ContentInViewNode`

Design note for D1376 and D1377, from Compose's `ContentInViewNode.kt`, `BringIntoViewRequestPriorityQueue.kt`, `UpdatableAnimationState.kt`, `BringIntoViewSpec.kt` and `BringIntoViewResponder.kt`, and kept to what was built.

## What Compose does

A request (`BringIntoViewRequester.bringIntoView`, a focused node) calls `bringIntoView` on the nearest `BringIntoViewModifierNode` with a bounds provider. Each responder node (`BringIntoViewResponderNode`) runs two coroutines side by side: its responder's suspending `bringChildIntoView(localRect)`, and the same request passed to its parent, whose bounds are `calculateRectForParent(localRect())`. The request returns when all of them have.

A scrollable's responder is its `ContentInViewNode`. A request that already shows returns at once. Otherwise it goes into a queue sorted by containment, where a request beside the others cancels them. If no animation runs, one starts: in `scroll(MutatePriority.Default)` it animates an `UpdatableAnimationState` (the spec's `scrollAnimationSpec`, a spring) to zero. Each frame scrolls by the fall. After the frame's layout, the requests that now show are resumed, smallest first, and the target is worked out again from the largest request that fits. The animation ends when nothing is left to scroll, and the rest are resumed. If the scroll is interrupted (a drag) or the node is detached, the rest are cancelled. If a frame's scroll isn't all taken (an edge), the animation is cancelled.

## How it fits compose-rs

**The walk.** compose-rs's tree passes a request on itself (D1371): `UiTree::bring_into_view_from` walks the entries before the requester in its chain, then each ancestor's, innermost first. That stays. A node that animates answers `ModifierNode::as_bring_into_view_responder` with a `BringIntoViewResponderNode` (compose-ui):

- `calculate_rect_for_parent(rect, scope)`: where the rect will be once shown.
- `bring_child_into_view(rect, parent, bounds, scope) -> Option<future>`: the future ends once it's shown or interrupted. Dropped, the request is withdrawn. `rect` is where it is as the walk asks, `parent` what `calculate_rect_for_parent` said of it, and `None` means nothing to wait for.

A node's answer, responder or at once, is found in one pass over its delegates.

The walk returns the futures, and the request waits for all of them (`join_all`), which stands for Compose's sibling coroutines. `NodeHandle::bring_into_view` returns that future. `UiTree::bring_into_view` (focus) launches it as a task of its own, since Compose's focusable launches its request too. Nodes that answer at once (`ModifierNode::bring_into_view`, the lazy layouts until C8) are still asked during the walk, with where the rect is then.

**The bounds.** `BringIntoViewBounds` is Compose's `() -> Rect?`. It holds a path: the base (the requester's entry and rect, a focused node, or where a node answering at once left it), the responders inside, and the responder it's for. Reading it peeks at the tree: the base's rect in the root now, through each responder's `calculate_rect_for_parent`, into the responder's layer. Entries are named by `EntryId` and nodes by generational `NodeId`, so a detached requester reads `None`. `BringIntoViewBounds::read` tells that apart from a tree it can't read now (`BoundsRead::Busy`: read from inside another read of it, for example by application code in a deprecated responder's `calculate_rect_for_parent`). A busy read isn't a requester gone: the container keeps what it read before, for `MOST_BUSY_READS` (8) reads in a row, after which the request is taken for gone (a read at the frame's end, the tree free, can't be busy: a debug assertion); the deprecated responder's `local_rect` keeps what it read before too, the walk's rect before its first read. Reading registers nothing (the scope's handle there isn't kept), so a read each frame costs no handle. The walk also asks each responder for its rect for the parent once, right away, to carry the rect on to nodes answering at once. Compose asks only when the parent reads it, so a spec is asked one more time here.

**The frame.** Compose's `afterFrame` runs after the frame's composition and layout. compose-rs runs frame awaiters before both, so the animation waits for the frame's end with a frame-end callback scheduled through the container's `CompositionLocalAnchor`, owned by its composition: another host's frame doesn't end it (one whose content may not have composed yet). The host runs these after drawing, then polls the woken tasks in the same frame. Each frame is: `with_frame_nanos`, scroll by the fall (before layout), wait for the frame's end, resume the requests that show, and set the new target.

**Scroll priority.** The animation is `state.scroll(MutatePriority::Default, …)`. A drag takes `UserInput` and interrupts it (D850): the task's `scroll` returns `MutationInterrupted`, and a guard dropped with the task cancels the requests left. A fling, also of the default priority, is interrupted by a request that comes during it, the newer scroll of a priority winning. A frame whose scroll isn't all taken calls `cancel_current_task`, which is compose-rs's form of Compose's `animationJob.cancel()`.

**The task.** It runs in the container entry's coroutine scope, through a handle the walk registers. Detaching the container, or disposing its composition, cancels it, and the guard cancels the requests.

**The queue and application code.** Reading a request's bounds may run application code (a deprecated responder's `calculate_rect_for_parent`), so the queue is never borrowed while one is read. Each request keeps the bounds it last read: the container reads them all (`refresh`) with nothing borrowed, then the queue decides from them (`enqueue`, finding the target). The requests a frame showed are decided outside the queue too, and resumed only while each is still its smallest. The queue is borrowed only for those decisions, never across an await, so the guard always finds it free. If it ever didn't, the guard would cancel the requests in a task of their own rather than leave them waiting (a debug assertion says so).

**The config.** A container's config is read when it's used: a frame's scroll takes the multiplier then, and a read of a request takes the pending scroll and the axis then. An update of the container mid-animation is followed, except for its state: the animation holds a scroll of the state it started with, until it ends.

**Signs.** As Compose, the spec is given offsets in the container's layout coordinates, left to right and top to bottom. The state is scrolled by `±delta`, with the sign set by the scrollable's `reverseDirection`. For `vertical_scroll` and `horizontal_scroll` that is `ScrollableDefaults.reverseDirection(layoutDirection, orientation, reverseScrolling)`, and for `scrollable` it's the parameter. D1371 gave a reversed or right-to-left scroll's spec mirrored offsets, so this is a change.

**The pending scroll.** A `vertical_scroll` lays out its own content. A request read between a scroll and its layout is moved by what the scroll still owes (`value - laid_out`), as in D1371. `scrollable` has no such knowledge, as in Compose.

**Keeping the focused child in view.** Compose's `onRemeasured`: a container measured smaller along its axis whose focused child showed before and is clipped now animates to keep it in view (`trackingFocusedChild`), its target the focused rect while no request is queued, until it shows. `vertical_scroll` and `horizontal_scroll` see the shrink in their own `measure` (a handle is made then, `MeasureScope::handle`); `scrollable`, which lays nothing out, is a `MeasuredSizeAwareModifierNode`. Being a `LayoutAwareModifierNode`, told of every placement, cost `column_scroll` 2 % and `first_frame_scrollables` 7 %; told of every measurement, about 1,000 instructions a scroll's first frame (`first_frame_scrollables` 1.1 %), which `scrollable` pays as Compose's `onRemeasured` does. Only a shrink makes their `ContentInView`.
- compose-rs can't read the tree during a measurement, so the shrink schedules a frame-end callback of the container's composition. It runs at the end of the same frame, with the layout done and the tree free, and the animation it starts takes its first step there, as Compose's does in the frame after the measurement. The focused child is read where it's placed then. A container laid out from its end (`!reverse_direction`, as Compose's adjustment) moved it by what the viewport lost, so that's added back to see where it was. More shrinks in the frame (a layout callback's write laid out again) make one check, from the size the first started at to the last. The check's handle is cancelled when the container is detached.
- The focused rect is `NodeHandle::focused_rect_inside` (compose-ui): the active target's focus rect in the container's layer, if it's after the container in its chain or in a node inside it, not an overlay's. Compose's scrollable delegates a focus target that never takes the focus to ask `getFocusedRect()`. compose-rs's `scrollable` would change every scrollable's focus grouping (text fields among them) for that, so it asks the tree. `vertical_scroll` and `horizontal_scroll` were targets already.

**Cost.** A container keeps `Option<Rc<ContentInView>>`, `None` until its first request. The queue, the animation state and the config are made then. A request for what shows already is answered in the walk, with the rect the walk has (`bring_child_into_view` is given it): no future, no task, no state, where Compose checks the same in the coroutine it launched. The visibility check reuses the rect for the parent (`bring_child_into_view` is given it too), so the spec, a walk up the composition's providers, is read once per container. A text field's own `scrollable` now answers a focus move's walk, as Compose's does: about 4,000 to 7,000 more instructions a focus move (`field_focus` +0.15 to +0.26 %, around its spread); nothing else moved. The follow-ups (bounds read outside the queue, keeping the focused child in view) moved no scenario beyond its spread, the display lists the same.

## What's left out

- Nested scrolling and overscroll during the animation. Compose scrolls through `ScrollingLogic`, so the connections around see the deltas. compose-rs finds connections only on a pointer's path (D1459), so `focusScroll_nestedScroll_childPartialConsumptionForSemantics` waits on nested-scroll-dispatcher.
- The lazy layouts still jump, and don't keep their focused item in view (C8).
- Keeping the focused child in view stops when the animation ends, or once the child shows, as Compose's. No test sees the second apart from the first: they differ only while a request is still queued after the focused child shows.
