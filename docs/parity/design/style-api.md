# Style API

The spec for the `style-api` feature of the [foundation-text-misc ledger](../foundation-text-misc.md#style-api): Compose foundation's `androidx.compose.foundation.style` package (`@ExperimentalFoundationStyleApi`), at the reference commit. Decisions D1580 to D1599 ([ui-and-layout](../../decisions/ui-and-layout.md#d1580)).

## 1. Compose's model

The package holds two designs. The first (`Style`, `StyleScope` with its 42 property interfaces, `Modifier.styleable(state, style)`, and its machinery: `ResolvedStyle`, `StyleableProperties` bit sets, `StyleOuterNode`, `StyleableAnimations`) is deprecated: "the stylable modifier, along with the predefined set of properties, are being removed". The second, which this port follows, is:

- **Properties.** `StyleProperty<T>(name, isLocal, defaultValue)` with an overridable `lerp`; `ProvidableStyleProperty<T>` is one a style may set. `stylePropertyOf(name, interpolate, default)` makes a property, `styleLocalOf` a *local*: a property a resolver's descendants inherit (read through their own resolver when they don't set it). The default interpolation dispatches on the runtime type: `Interpolatable` values (`Fill`, `Breadth`, `Shadows`, shapes), `Dp`, `Float`, `Int`, `Long`, `Color`, `TextUnit`; anything else jumps at half way. Value types: `Fill` (`None`, `Color`, `Brush`), `Breadth` (`None`, `Distance(Dp)`, `Fraction`), `Shadows` (`None`, `Simple`, `Compound`).
- **Styles.** `CommonStyle` is a `fun interface` whose `applyStyle` runs in a `CommonStyleScope`: `provide` a property, `state(key, block, active)` and its helpers (`pressed`, `hovered`, `focused`, `selected`, `checked`, `disabled`, `triStateToggle*`), `styleLayer`, `animate(toSpec, fromSpec)`, `provideNestedStyle`/`applyNestedStyle`, composition locals and density. `CommonStyle(a, b, …)` and `then` flatten into a `DualCommonStyle` or a `CombinedCommonStyle`; `CommonStyle` itself (the companion) is the empty style. `CustomStyle<ScopeT>` lets a design system define its own scope.
- **Layers.** A write wins over an earlier one unless the earlier one was in a deeper layer (`styleLayer`, which every `state` block is): `x = 10; styleLayer { x = 20 }; x = 30` gives 20. So a state's value wins over the base, whatever their order.
- **State.** `StyleState` (sealed; `MutableStyleState` is the only kind): predefined flags in one snapshot state object (enabled by default), custom keys (`StyleStateKey<T>(default)`, open, with `processInteraction`) in a snapshot map. Given an `InteractionSource`, its node collects it: presses, hovers and focuses set the flags (each counted, as `collectIs*AsState`), other interactions go to the custom keys.
- **Resolution.** `StyleResolver(style, state)` is remembered and bound to one `Modifier.styleResolver(resolver)` node (`StyleResolverNode`: traversable, observer, locals consumer). The node collects the style lazily, at the first `resolve { }` after it's bound, inside `observeReads`: a write to what the collection read (the state's flags, a local, the parent's nested keys) collects it again (`onObservedReadsChanged`). Collection (`StylePropertyCollector`) writes the values into `resolvedProperties`/`resolvedLocals`: snapshot maps of per-property `mutableStateOf` values each read through a `derivedStateOf` that lerps while the property animates. A property no longer set goes back to its default (animated if it was), and is dropped once neither collection set it.
- **Application.** Separate modifiers read the resolver: `styleAppearance` (`Modifier.appearance { }`: a draw node; shape, background, foreground, border, drop and inner shadows), `stylePlacement` (`Modifier.placement { }`: a layout node; left/top/right/bottom offsets, min/max sizes, width/height as a distance or a fraction), `styleGraphicsLayer` (`Modifier.graphicsLayer(layerRequired) { }`: alpha, transforms, clip, colour filter; placed with a layer only if one of them is set), and `styleContentPadding`/`styleExternalPadding`/`styleBorderPadding` (`Modifier.padding(PaddingValues)` reading the resolver). The deprecated `styleable(resolver)` chains them: resolver, external padding, graphics layer, placement, appearance, border padding, content padding.
- **Invalidation.** Each applying node reads only its own properties, each a state: a change of background redraws the appearance node and nothing else; a change of width measures the placement node again; a change of alpha updates the layer only (its block is the layer's, observed apart). A property becoming set or unset changes the map, which every reader observed.
- **Animation.** `animate(spec) { }` marks the writes inside as animated, with `toSpec` for the change into the state and `fromSpec` for the change out of it (the property animates on the way back with the spec of the block that set it before). On each collection the properties animated now or before that changed get an entry (`StyleAnimations`): an `Animatable(0f)` run to 1 with the spec, its value lerping the start (the value shown when it started, so an interruption starts from where it was) to the end. Entries are dropped when their animation ends.
- **Locals for content.** `contentFill` (with `contentColor` and `contentBrush` accessors) and the text properties (font size, weight, family, …) are style locals: a descendant's resolver reads them. Nothing in foundation's text reads them yet.

## 2. compose-rs's mapping

**Module** `compose_foundation::style`, all of it behind no feature flag (Compose's opt-in annotation has no Rust counterpart; the items say they're experimental).

**Properties (D1581).** `StyleProperty<T>` holds its name, whether it's local, its default (`fn() -> T`) and its lerp (`fn(&T, &T, f32) -> T`); `ProvidableStyleProperty<T>` wraps one. They're declared as `static`s with `const fn`s (`style_property_of`, `style_property_of_with`, `style_local_of`, …), as `CompositionLocal`s are, and identified by name and value type (an address isn't an identity: a `const` has a new one at each use). The default interpolation is a trait, `StyleInterpolate`, with Compose's interpolations for its types and a jump at half way for the rest (an app's type implements it with an empty `impl`). The predefined properties (background, border, padding, sizes, transforms, content fill, text) are public statics in `style::properties` (D1580).

**Styles and scopes (D1582).** `CommonStyle` is an `Rc` of a closure taking `&mut dyn CommonStyleScope`, with `CommonStyle::EMPTY` and the flattening combinators. A block is handed the scope (a closure can't hold `&mut scope` while the scope runs it), so the scope's interfaces are one object-safe trait, `CommonStyleScope`, over `CustomStyleScope` (provide, density, locals); the generic helpers (`provide`, `state`, `pressed`, `animate`, …) are an extension trait for every scope.

**Resolution (D1583).** `StyleResolver` is an `Rc` handle. Collection is a method of the resolver given a context (density, locals, a coroutine scope for its animations, its parent resolver), so it runs without a tree (the host tests) and from the node's callbacks: `on_attach` (bind, find the parent resolver through `traverse_ancestors`, collect inside `observe_reads`), `on_observed_reads_changed` (collect again), an update that swaps the resolver (unbind the old, bind the new, collect). Compose collects lazily, at the first read; compose-rs's readers (a draw, a measurement) have no context to collect with, so it collects eagerly in those callbacks, before any layout reads it. A child attached before its parent (children attach first) reads its parent's locals and nested styles as states, so the parent's first collection collects the child again before the frame lays out.

Resolved values are a list of slots, each a snapshot state holding the value and its animation, plus one state of the list's membership: a reader of a property observes its slot and the membership, as Compose's reader observes its value's state and the map. So a background change redraws only the appearance node, a width change measures only the placement node, an alpha change updates only the layer: compose-rs observes reads in measuring and drawing, which gives what Compose's `observeReads` in those nodes does.

**State (D1584).** `StyleState` is an `Rc` handle (`MutableStyleState` derefs to it): the flags in one `u32` state, custom keys in one state of a small list. `StyleStateKey<T>` is a `static` identified by name and type, its interaction handler a function. The node listens to the source (`InteractionSource::listen`, D1057) instead of a collecting task.

**Applying modifiers.** `Modifier::appearance`, `placement`, `style_graphics_layer_with` (Compose's style `graphicsLayer(layerRequired, block)`: compose-rs's `graphics_layer` is taken), and the `style_*` forms over a resolver, each a custom element with its node: appearance draws with `BorderRenderer` and the shadow painters; placement is Compose's measure; the graphics layer places with a `LayerBlock` kept by the node so its reads update the layer only. Padding reads the resolver in a layout node (Compose's `padding(PaddingValues)`).

**Animation (D1585, step 2).** The collector records specs as Compose's; entries run on the resolver node's coroutine scope (an `Animatable<f32>` to 1); a slot's state holds its entry, so starting one notifies that property's readers only, and the animatable's value is a state its readers observe.

**Locals for content (D1586, step 3).** The content fill and text properties are style locals in `style::properties`, with `content_color`, `content_brush`, `content_fill` accessors.

**Cost.** Nothing outside the new module changes: a node that doesn't use styles runs no new code.

## 3. Tests

Host tests (`StyleCollectorTest`, `StyleStateTest`, `StylePropertyTest`, `CommonStyleTest`, `StyleResolverNodeTest`) are rewritten against the resolver's test hooks (`collect_for_test`, `bind_parent_for_test`); the device tests, written for the deprecated `styleable(state, style)`, are rewritten over the resolver chain (a `styleable` helper in the test, as Compose's deprecated `styleable(resolver)`) with the predefined properties, running in `compose-test`.
