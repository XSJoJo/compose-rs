# Text context menu and toolbar

Design note, written before the code (built: step 1, D2031; step 3's toolbar, D2032; step 5, D2033; step 2's state and position, D2034; a review's fixes, D2035; step 2's look and area, D2036; the default dropdown, D2037; Compose's default providers' composable, D2038; the dropdown's position at placement, D2039), from Compose's `text/contextmenu/**` (builder, data, modifier, provider, internal), `contextmenu/**` (the dropdown's state, popup position, items and area), ui's `TextToolbar`, `TextFieldSelectionState`'s and `SelectionManager`'s toolbar, and their tests. It covers [`text-context-menu`](../foundation-text-misc.md#text-context-menu): the menu a right click opens on a field or a selection, and the floating toolbar a finger's selection shows, with the hooks [touch text selection](touch-text-selection.md) left (the cursor handle's tap, the dragged handle, `selected_region_rect`).

Compose has two paths behind `ComposeFoundationFlags.isNewContextMenuEnabled`. The flag is on at tip on Android (`isNewContextMenuInitiallyEnabled`), and its device tests run both ways (`ContextMenuFlagFlipperRunner`); compose-rs ports the new path, whose tests are those that run with the flag on. The old path's own internals (`TextFieldSelectionManager`'s `contextMenuBuilder`, `MenuItemsAvailability`, the legacy field) are `n/a`; ui's `TextToolbar` and `LocalTextToolbar` stay as public API.

## Layers

- **compose-ui: the platform's toolbar.** Compose's `TextToolbar` (`show_menu(rect, on_copy, on_paste, on_cut, on_select_all, on_autofill)`, `hide`, `status`) and `LOCAL_TEXT_TOOLBAR`, read from the tree as `LOCAL_CLIPBOARD_MANAGER` is. Under it, the platform hook both paths use, shaped as Android's floating `ActionMode`, which is what Compose's `AndroidTextToolbar` and `AndroidTextContextMenuToolbarProvider` both drive:
  - `TextActionModes::start(callback) -> Option<Rc<dyn TextActionMode>>` (`View.startActionMode(callback, TYPE_FLOATING)`), set on the tree by the host (`UiTree::set_text_action_modes`); none on desktop and headless;
  - `TextActionMode`: `invalidate`, `invalidate_content_rect`, `finish`;
  - `TextActionModeCallback`: `on_get_content_rect` (in the root), `on_create_action_mode` and `on_prepare_action_mode` filling a `TextActionMenu` (group, id, order, title and a click action per item, as `Menu.add` with `setOnMenuItemClickListener`), `on_destroy_action_mode`. Compose's internal `TextActionModeCallback` is this, its `callbackInjector` the test's spy.
  - `LOCAL_TEXT_TOOLBAR`'s default is a `TextToolbar` over the tree's action modes (Compose's `AndroidTextToolbar`: the five items with Android's ids, in Compose's order), doing nothing without them.
- **compose-foundation: Compose's API.** `text_context_menu::{builder, data, modifier, provider}` as Compose's packages: `TextContextMenuData`, `TextContextMenuComponent` (an enum: an item or a separator; the classification item is `smart-selection`'s), `TextContextMenuItem` (key, label, leading icon as a `Painter`, click with the session), `TextContextMenuKeys`, `TextContextMenuSession`, `TextContextMenuBuilderScope` (`item`, `separator`, Compose's collapsing and filtering), `Modifier::append_text_context_menu_components` and `filter_text_context_menu_components` (traversable nodes of one key, collected bottom to top, filters after builders), `TextContextMenuProvider`, `TextContextMenuDataProvider`, `LOCAL_TEXT_CONTEXT_MENU_DROPDOWN_PROVIDER` and `LOCAL_TEXT_CONTEXT_MENU_TOOLBAR_PROVIDER`. The internals tests reach (`ProvideBasicTextContextMenu`, the toolbar handler and its requester, the providers, `collect_text_context_menu_data`) are public and hidden, as compose-rs does for its tests outside the crate.
- **compose-foundation: the dropdown.** Compose's `contextmenu/` internals: `ContextMenuState`, `ContextMenuPopupPositionProvider`, the column of items with Compose's `ContextMenuSpec` sizes and colors, `ContextMenuArea` and the right-click detector over compose-ui's pointer buttons. Built (D2036): the scope collects items and separators into a list its builder's caller composes in order (Compose's is a state list of composables), a label a `String`, an icon a function of its color; the builder block is an `Rc<dyn Fn(&mut ContextMenuScope)>`, a composable's callbacks taking their arguments by value; the colors are Compose's defaults on every platform (Android's resolve the theme's `Widget.PopupMenu` styles, which compose-rs doesn't read: a dark theme's menu stays light). The default dropdown provider is a compose-rs `Popup` at the click, focusable, closed by a click outside or the back key, as Compose's `DefaultTextContextMenuDropdownProvider`; its position asked as the popup is placed, where compose-ui opens the tree to read (D2039).
- **compose-android: the floating toolbar.** The host's `TextActionModes` goes through JNI to `ComposeRsView.startTextActionMode`, which starts an `ActionMode.Callback2` of `TYPE_FLOATING`; its `onCreateActionMode` and `onPrepareActionMode` ask Rust for the menu (titles, groups, ids, orders), each item's click calls Rust back, `onGetContentRect` asks Rust for the rect (in the view: compose-rs's root is the view), `onDestroyActionMode` tells Rust. A mode is named by an id on both sides; Rust's `invalidate`, `invalidate_content_rect` and `finish` call the view's methods for that id.
- **compose-test: a test toolbar.** The rule installs `TestTextToolbar`, a `TextActionModes` behaving as Android's floating mode does for Compose's tests through their spy: `start` creates the menu (a mode whose menu is empty isn't started), `invalidate` prepares it again, `invalidate_content_rect` reads the rect again, `finish` destroys it. Tests read `shown()`, `items()`, `content_rect()`, click an item by title, or dismiss it as a touch outside does. Compose's device tests check the real platform's toolbar; compose-rs's check this one, and the phone checks the real one.

## Providers and sessions

`TextContextMenuProvider::show_text_context_menu(data_provider)` returns a boxed future that ends when the menu closes, as Compose's `suspend fun` does: dropping it (its job cancelled) closes the menu, as Compose's `finally`. A session is a signal its future waits on (Compose's `Channel`), closed by an item's click or the platform. Both default providers keep Compose's `MutatorMutex`: a new menu replaces the open one, whose future ends.

**What's read is observed.** `TextContextMenuDataProvider`'s `position`, `content_bounds` and `data` read state, as Compose's snapshot-aware functions; the platform toolbar's provider runs them under a `ReadObserver` (Compose's `SnapshotStateObserver`) and invalidates the mode (its items) or its rect when what they read changes, in a task, as Compose's executor posts. The dropdown reads its data in composition and its position as its popup is placed (D2039), as Compose's.

**The toolbar's rect is in the window**, the host's view: Compose's `positionInRoot` is in the view its mode starts on, a popup's or a dialog's own window; compose-rs's popups and dialogs are placed in the host's one view, so the provider translates by `position_in_window` (D2035).

**The anchors.** Compose's `ProvideBasicTextContextMenu` and `ProvidePlatformTextContextMenuToolbar` wrap content in a `Box(propagateMinConstraints = true)` whose coordinates (a state written by `on_globally_positioned`, never equal, so a move is a change) are the destination the data provider places the menu in. Ported as they are.

**The defaults, without their composition.** Compose's fields and containers wrap their content in `ProvideDefaultPlatformTextContextMenuProviders`, which provides both when none is: a `Box`, its coordinates' state, two remembered providers and an effect per field, composed whether or not a menu ever opens. compose-rs keeps Compose's locals (null by default, provided over a subtree to replace them) and, where they're null, a field or a container uses the tree's default providers: the platform toolbar, made when the toolbar shows and anchored at the field or the container (D2035: one per tree, anchored at the first field's root, put a later field's rect in a closed popup's coordinates), and a dropdown composed in the field's or the container's handles' composable (already composed in the inner field and after the container's content) while a menu is open. The behavior is Compose's (a provided one wins; without one, the platform's); the composition costs nothing until a menu opens. Compose's `ProvideDefaultPlatformTextContextMenuProviders` is there too, hidden, for its tests and content wanting Compose's shape (D2038); `TextContextMenuProvider` is `Any`, so a test tells what it was given by its type.

## The toolbar's handler

Compose's `textContextMenuToolbarHandler(requester, onShow, onHide, computeContentBounds)` is a node that shows the toolbar through the toolbar provider in a job, with itself as the data provider (its `data` collected from where it is, its `contentBounds` its owner's). Ported as it is for the container and Compose's tests (`ToolbarRequester` in a test is the same, its show panicking before any node attached it, as Compose's `checkPrecondition`). Its logic is a struct the field's node embeds too: the field doesn't add a node to every field's chain, and its data provider reads the field node through its handle when asked, outside the field's own callbacks.

## The field

The field's node keeps Compose's `TextToolbarState` (`None`, `Cursor`, `Selection`), set where Compose's `TextFieldSelectionState` sets it: a tap on the cursor handle toggles `Cursor`; a long press, a double tap and a handle drag's end (with a selection) set `Selection`; a tap and an edit (Compose's `observeTextChanges`) set `None`; a hardware key or a mouse ends the touch interaction and the focus leaving ends what shows it, which hide it without changing the state; `SetSelection` semantics set `Selection` when not in traversal mode. At the end of its measurement, only while that state isn't `None` or a toolbar is shown, it computes Compose's `derivedVisibleContentBounds`: shown for a collapsed selection in `Cursor` or a selection in `Selection`, while no handle is dragged and the user touches it, the content rect (the cursor, or the selection's handles from the top of their lines) intersected with the field's visible bounds; none when they don't overlap. It shows the toolbar when that rect appears and hides it when it goes (Compose's `distinctUntilChangedBy { it == null }`); the rect itself is a state the data provider's bounds read, so the toolbar follows it.

**Its items** are Compose's `addBasicTextFieldTextContextMenuComponents`, the field node's own components, collected before its ancestors' (Compose's builder sits on the decoration box, the nearest; a modifier there costs at every recomposition, D2032): cut (a selection, editable, not a password), copy (a selection, not a password), paste (editable, the clipboard holding text when the toolbar showed: Compose's `ClipboardPasteState`, updated in the handler's `onShow`, D2035), select all (not everything selected), each closing the menu after its action, but select all, which asks for the selection's toolbar and closes the menu only while no toolbar shows (Compose's `textToolbarShown`: shown, not asked for). Compose's autofill item (a collapsed selection, editable) waits on autofill: with nothing to ask, it would do nothing (D2035). What applies the node tells through the field's shared `TouchHandles` (a state, so the toolbar's items follow it); the actions reach the node through its handle.

**Its right click** is Compose's `showTextContextMenuOnSecondaryClick` on the field's box: a secondary button's press opens the dropdown at the press with the same builder's items; the press places the cursor first when outside the selection, as Compose's `onPreShowContextMenu`.

## The container

`SelectionContainer` keeps Compose's `SelectionManager` toolbar: shown in touch mode after a long press, a double tap or a handle's drag end, while the selection isn't collapsed and its region (`selected_region_rect`, kept in the visible bounds) overlaps the container's; hidden by a tap, a drag, a mouse, a cleared selection or the container leaving. Its items are copy and select all (Compose's `SelectionManager.contextMenuBuilder`); its right click opens the dropdown with them. The tree tells foundation's composable through `ContainerHandles`, which the handler reads.

## Costs

- A field: no node, no composition and no state read until its toolbar state leaves `None` or a right click comes: a branch at the end of its measurement.
- A text outside a container: nothing. A container: what it does now; the toolbar's checks only with a selection.
- Checked with `compare_instructions.py` at fat LTO: the field and selection scenarios within their spread.
